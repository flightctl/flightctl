The problem space

Linux keeps escaping the datacenter

Same OS, same containers, same tooling instincts — radically different operating conditions.

Retail & hospitality

Point-of-sale terminals, kiosks, digital signage. Thousands of sites, no IT staff on site.

Industrial & robotics

Factory controllers, AMRs, machine-vision inspection. Downtime is measured in lost production.

Energy & utilities

Solar inverters, substation gateways, metering. Physically exposed, cellular-only backhaul.

Transport & healthcare

In-vehicle compute, toll systems, bedside and imaging devices. Regulated and safety-relevant.

  • Scale × distribution10 sites is a spreadsheet. 10,000 sites is a distributed systems problem.
  • Hostile networksPrivate, NAT'd, cellular, intermittent. Often no inbound reachability at all.
  • No hands on siteA failed update can mean a truck roll. Sometimes to an oil rig.
  • Physical exposureTampering, theft, cloning. The device is not in your building.
  • Constrained hardwareCPU, memory, storage, power and thermal budgets.

Why not just…

The tools we already love don't quite fit

Each assumes something the device edge doesn't give you.

Push-based config management

Ansible, Puppet, Salt — excellent tools, wrong assumption.

  • Needs to reach the device now; devices are offline or NAT'd
  • Mutable hosts drift apart over years
  • A half-applied run leaves no way back

Kubernetes everywhere

Great model, heavy assumptions.

  • Control plane expects a stable, low-latency network
  • A node is disposable; a device in a hospital is not
  • Doesn't manage the host OS itself — the part that bricks

Scripts + golden images

Where most teams actually start.

  • Works at 10 devices, collapses at 10,000
  • No inventory, no staged rollout, no audit trail
  • Every team rebuilds the same fleet controller, badly
Flight Control isn't a replacement for any of these — it borrows the declarative API model from Kubernetes, delegates OS updates to bootc and workloads to Podman/MicroShift, and fills in the part nobody owns: the fleet.

Flight Control

Simple, scalable, and secure management of Linux edge fleets

Declare the OS, the config, and the apps you want. The fleet converges.

Started 2023 · Apache 2.0 · Go

  • Declarative, Kubernetes-like API — without requiring KubernetesFamiliar to anyone who has written a kind: and a selector:, but a shallow learning curve if you haven't.
  • Opinionated out of the boxA working operating model on day one, not a construction kit. Escape hatches exist when you outgrow it.

3:15 – 4:15

This is the thesis slide. If someone only remembers one slide, make it this one.

"Kubernetes-like without Kubernetes" usually gets a reaction — be ready for the follow-up. The honest answer: we took the API ergonomics (declarative spec/status, labels, selectors, controllers reconciling) and deliberately left behind the runtime assumptions (etcd quorum, always-on control plane, pods as the unit of everything).

The "opinionated" bullet matters to this crowd — some will hear it as "inflexible". Pre-empt: there are lifecycle hooks and a remote console for when the model runs out.

Architecture

A service, an agent, and one rule: the device always calls home

4:15 – 6:15  |  longest slide, budget for it

Build it in four steps (press → between each):

  • Service + users. API server, workers, Postgres. Two API endpoints, two auth mechanisms — that separation matters, come back to it on slide 11.
  • Device + the arrow. The single most important detail in the talk: the arrow points left. The device initiates every connection. That's what makes NAT, cellular, and firewalled sites work without a VPN or a bastion, and it's why there's no inbound attack surface on the device.
  • Providers. All pluggable — you bring your own IdP and CA. Nothing here is Red Hat-specific.
  • Config sources. The service resolves Git/OCI/Secret/HTTP references server-side and hands the agent a flat, resolved spec. Devices never need credentials for your Git server.

Worth saying out loud: the service runs on Kubernetes or on a single RHEL box with Podman quadlets. Kubernetes is not a prerequisite for using this.

Likely question: "polling — what's the latency?" Answer: poll interval is configurable (default order of seconds-to-minutes); it's a deliberate trade of freshness for scale and network tolerance.

The API

Everything is a resource with a spec and a status

Desired state goes down. Observed state comes back up. Controllers close the loop.

  • Declarative means the agent can act aloneThe spec describes the goal, not the steps. An offline device still knows what it is supposed to become, and can get there without asking.

6:15 – 7:30

Don't enumerate the pills — let people scan them. Just note the alpha ones are the newest surface area and the place where community input actually changes the API.

The YAML is the payoff: point at spec.os.image vs status.os.image and the Updating status. That one status message — "downloaded, waiting for the update window" — encodes two design decisions we'll unpack next: download-before-apply, and scheduled maintenance windows.

For a Kubernetes-literate crowd: yes, ResourceSync is basically Argo/Flux for devices, and no, you don't need a cluster to run it.

What you declare — 1 of 2

Operating system and host configuration

  • Image-mode OS, so drift can't accumulateThe agent orchestrates the update but delegates execution to bootc (or rpm-ostree). Every device with the same image tag is bit-for-bit the same host.
  • Config as logical layers on top of the imageFetch from Git, an OCI artifact, a K8s Secret, HTTP, or inline. The service resolves the sources; the agent just applies files and signals systemd to reload — usually with no reboot.
  • Download first, then apply transactionallyEvery asset lands on disk before anything changes. If the update or the Greenboot health checks fail, the device returns to the previous OS and the previous config. No truck roll.
  • Maintenance windows, per device or per fleetSeparate schedules for downloading and for applying. Update the shop floor at 4am on Mondays, not during a shift.
Escape hatch: device lifecycle hooks run your own scripts before/after updates, and a remote console gets you a shell when the model isn't enough.
spec:
  os:
    image: quay.io/acme/pos:v2.4

  config:
    - name: site-network
      gitRef:
        repository: site-configs
        targetRevision: v1
        path: /network/berlin-04
    - name: motd
      inline:
        - path: /etc/motd
          content: Managed by flightctl.

  updatePolicy:
    downloadSchedule:
      at: "0 2 * * *"
      startGraceDuration: "30m"
    updateSchedule:
      at: "0 4 * * 1"       # Mon 4am
      timeZone: Europe/Berlin
      startGraceDuration: "1h"

7:30 – 9:00

Two things to make vivid here, because they're what people actually lose sleep over:

  • Download-then-apply. Say it plainly: "the agent will not touch a running system until every byte it needs is already on disk." Cellular device on a 20-minute connectivity window — this is the difference between an update landing and a brick.
  • Rollback covers config too, not just the OS image. That surprises people who've used ostree directly.

The startGraceDuration field is a nice detail if there's appetite — it exists because a device that was asleep at 4am shouldn't miss its window forever.

Package-mode RHEL is supported too, but be precise if it comes up: there Flight Control manages configuration and applications only — the agent detects it isn't in image mode and leaves OS updates to your existing dnf workflow. Mention only if asked.

What you declare — 2 of 2

Application workloads

  • Containers, VMs, and Kubernetes — one APIPodman containers, Quadlets, and compose; virtual machines; MicroShift when a workload genuinely needs Kubernetes. Same applications: list either way.
  • Virtual machines are first-classDeclare a KubeVirt VirtualMachine; the service renders it to Quadlets and the agent runs it on KVM. That legacy Windows app runs next to your containers — managed the same way, rolled out the same way.
  • Apps ship as OCI artifacts or imagesPackaged and versioned in a registry you already run — or defined inline in the spec for small things.
  • Volumes can be OCI artifacts tooShip an AI model, a config bundle, or static assets as a versioned artifact and mount it. Update the model without rebuilding the app.
  • The agent watches, not just installsPer-application health rolls up into device status and into the fleet summary. A crash-looping container is visible centrally, not just in a log nobody reads.
spec:
  applications:
    - name: checkout
      appType: quadlet
      image: quay.io/acme/checkout:v7
      volumes:
        - name: pricing-model
          image:
            reference: quay.io/acme/
              pricing-model:2026-09
    - name: back-office   # the app nobody
      appType: vm          # dares rewrite
      publishPorts: ["3389:3389"]
      inline:
        - path: vm.yaml
          content: |
            apiVersion: kubevirt.io/v1
            kind: VirtualMachine
            metadata:
              name: back-office
            spec: { ... }

9:00 – 10:00

Move briskly — this slide is more "yes, that works the way you'd hope" than a new concept.

Spend a beat on the VM bullet. It's the one that surprises people. The edge is full of software that will never be containerized — a Windows POS backend, a vendor's HMI, a 2011 Java app with a licence dongle. You declare a KubeVirt VirtualMachine manifest inline, the control plane renders it to Quadlet units, and the agent runs it on KVM on the device. No Kubernetes involved — just the manifest format, because it's the one people already know.

Be honest about the boundary: Flight Control manages the VM's lifecycle — deploy, start, stop, restart, roll out a new disk image — not what's inside it. Inside stays your problem, with Ansible or whatever you use today. That honesty lands better than overclaiming.

The OCI-artifact-as-volume bullet is the other one worth a beat. Concrete framing: "ship a new pricing model or a new vision model to 4,000 stores by bumping one tag — the app container doesn't change, so nothing restarts that doesn't have to." AI-at-the-edge people light up at this.

If asked "why Quadlets and not just compose?" — both are supported; Quadlets give you systemd semantics (ordering, restart policy, journald) which matters on a device with no orchestrator above it.

Other likely VM questions: needs /dev/kvm and CPU virt extensions; the virt runtime ships in the device OS image; Windows guests work (UEFI, TPM, VirtIO drivers, RDP published via publishPorts).

Scaling out

From one device to ten thousand: fleets

Devices are never assigned to a fleet. A fleet selects them — including the ones that don't exist yet.

  • Labels are the organizing primitiveLocation, hardware model, purpose, rollout stage. Devices can self-label at enrollment from system info — zero-touch fleet assignment.
  • One template, many devicesThe fleet controller copies the rendered template into each device's spec. From there it's the same reconcile loop as a single device.
  • Overlaps are detected, not silently resolvedTwo fleets selecting one device? It keeps its current fleet and raises MultipleOwners.

10:00 – 11:15

The line that makes this click: "you never add a device to a fleet — you give it labels, and the fleet finds it."

Build to the green box and dwell there. Tomorrow's device is the point. The enrollment-time label-from-systeminfo feature means a tech can unbox hardware, plug it in, and it lands in the right fleet with the right OS and apps without anyone touching the console.

The MultipleOwners detail signals maturity to this audience — we chose to surface the ambiguity rather than pick a winner.

Scaling out

Rollouts you can survive

Changing one device is easy. Changing ten thousand without taking down the business is the hard part.

Batch sequence

Ordered batches, selected by label and/or a count or percentage. They run one after another.

  • Canary, then 1% of EMEA, then the rest of EMEA, then everything
  • An implicit final batch sweeps up the remainder

Success threshold

A batch must hit its success ratio before the next one starts. Otherwise the rollout stops and waits for a human.

  • A bad image reaches your canaries, not your revenue

Disruption budget

Orthogonal to batching: cap how many devices are down at once, grouped by any label.

  • groupBy: [store], minAvailable: 2 — every store keeps two working tills, always

Per-device windows still apply

The rollout picks devices; the device decides when it may act.

  • Selected at noon, applies at 4am local — OutOfDate in between
spec:
  rolloutPolicy:
    deviceSelection:
      strategy: BatchSequence
      sequence:
        - selector:
            matchLabels: { stage: canary }
          limit: 1
        - selector:
            matchLabels: { region: emea }
          limit: 1%
        - selector:
            matchLabels: { region: emea }
        - limit: 10%
      # + implicit final batch

    successThreshold: 95%

    disruptionBudget:
      groupBy: [store]
      minAvailable: 2

11:15 – 12:30

Frame this as the slide that separates a demo from a production system. "Anyone can push a config to a device. The hard part is pushing it to ten thousand devices and still having a business in the morning."

Walk the YAML top to bottom — it reads almost like English and the audience will follow it faster than the cards.

The disruption budget is the subtlest idea: it's not about order, it's about concurrency within a group. The two-tills-per-store example is the clearest way to land it.

Honest caveat if it comes up: this is currently a single strategy (BatchSequence). Richer strategies — and status-driven prioritization — are on the list, and it's a good area to contribute.

Security

Identity from unboxing to decommission

The device is in a parking garage. Assume someone will open it.

1

Provision

Device is imaged with the OS, the agent, and an enrollment config that binds it to your service. Nothing secret is baked in.

2

Generate identity

On first boot the agent creates a keypair. The private key never leaves the TPM — it can't be extracted or cloned onto other hardware.

3

Request enrollment

Agent submits a TCG-compliant CSR plus system inventory, with cryptographic proof of possession by a live TPM and a chain back to the manufacturer.

4

Approve

A human — or a policy — approves, optionally assigning labels. Only then is a device record created and a client certificate issued.

5

Operate

Every call is mTLS on a separate agent-facing endpoint. Certificates rotate automatically before expiry. Users authenticate separately, via your IdP.

6

Decommission

The service instructs the agent to destroy its private key, making the identity permanently unusable, and records the device as decommissioned.

No inbound attack surface

The device listens for nothing. There is no port to scan, no VPN concentrator to compromise, no bastion to protect.

Two endpoints, two trust models

Users get JWTs from your OIDC provider; devices get X.509 from your CA. A stolen user token is not a device, and vice versa.

Bring your own everything

Keycloak, generic OIDC, OpenShift OAuth, AAP, or PAM for authn. SpiceDB or Kubernetes RBAC for authz. Built-in CA or cert-manager.

12:30 – 14:00

Open with the threat model, not the mechanism: "the physical security assumption you get for free in a datacenter is exactly the one you don't have here."

Step 2 is the crux. Spell out the consequence: if someone steals the disk and clones it, the clone cannot authenticate, because the key lives in that specific TPM. That's the whole reason for hardware root of trust, stated in one sentence.

Step 4 — "friction-free but not zero-trust-free". Approval is a real gate; it's also automatable, which is where a lot of current work is going.

Step 6 usually gets a nod from anyone who's had to account for lost hardware in an audit.

Likely question: "what if there's no TPM?" File-based keys are supported; you lose clone resistance, and that's an explicit, documented trade.

Day 2

Knowing what's actually happening out there

Status that rolls up

Device, application, and update status aggregate into a live fleet summary. The agent pushes on change rather than being polled, so it stays cheap on constrained hardware and metered links.

Resource monitors & alerts

Declare CPU, memory, and disk thresholds in the device spec. The agent evaluates them locally — and keeps evaluating them while offline. Alerts surface through Alertmanager.

Metrics & traces

Prometheus metrics for the service, an OpenTelemetry gateway for device-side telemetry. Standard tooling, no bespoke dashboard required.

Vulnerability view

Scan the OS images your fleet is actually running and see CVEs by severity, per device and per fleet. Answers "are we exposed, and where?" without an inventory spreadsheet.

Remote console

A shell on a device that has no reachable address, over the connection the agent already holds open. For when the declarative model runs out.

Air-gapped operation

Fully offline installs, offline RPM repositories, and portable-media workflows for sites with no internet at all.

Worth emphasizing: resource monitors keep working offline. A device that loses connectivity for a week still evaluates its own health rules and reports the backlog when it reconnects.

Newest surface area

Building and distributing what you ship

Managing devices is half the job. Producing the images and apps they run is the other half.

ImageBuild alpha

Build a bootc image with the agent already embedded — through the API, not a laptop.

  • Generates the Containerfile, builds, pushes
  • Optional SBOM generation and publication as an OCI referrer
  • Handles enrollment certificate binding

ImageExport alpha

Turn that image into something a factory or a technician can actually flash.

  • qcow2, vmdk, ISO
  • Same declarative resource, same audit trail

Catalog alpha

A versioned index of what's deployable: apps, system images, AI models.

  • Versions with explicit upgrade paths
  • Publisher metadata, icons, support links
  • Groundwork for click-to-deploy in the UI
These three close the loop: build an image → publish it to a catalog → point a fleet at it → watch it roll out — all through the same API, all reviewable in Git. They're also the least settled part of the project, which makes them the most interesting place to have an opinion.

22:00 – 23:00

The numbers are there to establish that this is a real, active project rather than a demo — don't dwell, let them be read.

Only the boxed items get said out loud. The five lines under 1.4 are there to be scanned, not read.

Package-mode RHEL — the objection you get all day is "image mode is a big commitment and my fleet isn't there yet." As of 1.3 that's no longer a prerequisite. Be precise about the boundary, because it's a fair question: on a package-mode host Flight Control manages configuration and applications, and the agent detects it isn't in image mode and won't attempt OS updates. Your dnf workflow stays yours. RHEL only for now — Debian and Ubuntu are deferred.

Virtual machines — callback to the applications slide. Say plainly: this shipped, it isn't a plan. Scope for the first iteration is deploy / start / stop / restart on KVM-libvirt, with sane default networking and storage; graphical console access and catalog integration are follow-on work. If someone asks about live migration or HA, the answer is no — this is a single-device hypervisor story, not a virtualization platform.

First-boot customization — the concrete scenario sells this: a site where DHCP isn't permitted, so someone physically present has to supply a static IP, a proxy, or a licence token before the device can reach anything. Customers were building their own bespoke first-boot services for this and baking them into the image. Now it's out of the box, and it runs before enrollment and fleet assignment.

MLOps at the edge — inference at the edge is the single most-asked-for thing right now, and today people hand-roll it. The design point is worth stating out loud: Flight Control is the orchestrator, not the MLOps platform — training and model curation stay in tools built for that. What 1.4 adds is the deployment half: inference runtime and model as independently versioned catalog items, pushed to GPU-capable fleets under the same rollout policies, with telemetry coming back through the OTel gateway. Ties straight to the OCI-artifact volumes on the applications slide.

Delta updates — the honest framing: a bootc image is 1–2 GB, and a site on cellular or satellite cannot pull that on every change. Note the history if it helps — rpm-ostree had delta upgrades and image mode lost them; this gets the capability back, built on oci-delta. Two details worth having ready: it falls back transparently to a full pull when no usable delta exists, and unlike registry-side tricks it works fully offline, which is the case that actually matters here.

The rest is deliberately specific — vague roadmaps don't attract contributors. If anything there sounds interesting to someone in the room, that's the conversation to have afterwards.
